## Outcome

The whole-app acceptance loop is now explicit:

```text
upload resume -> ask for suitable jobs -> current source-backed recommendations
-> select target -> focused evidence questions -> truthful draft -> review/accept
-> download DOCX or PDF -> continue with the next suitable jobs
```

The tailored version, prior conversation, candidate evidence, preferences, targets,
applications, and decisions must remain available across that loop. A conversation is
not a candidate-identity boundary. If the user explicitly works for another person,
that person receives a separate candidate context; ordinary role pivots never silently
switch identity or merge two candidates.

The recruitment team now studies the selected resume, maintains a visible plan,
searches the current Singapore corpus, ranks roles with evidence and descriptive pay
context, handles mid-conversation changes, drafts evidence-safe edits, and follows the
new resume version after an accepted edit.

## Durable cautions

- A green unit suite is not proof of model stopping, tool selection, streaming, or
  rendered behavior. Repeat browser acceptance when those seams change.
- A failed search is unknown, never zero results. Missing salary is unknown, never the
  peer median.
- Tool refusals must include the actionable alternative or missing identifier; opaque
  refusals can cause repeated calls until the step cap.
- Model work stays outside the conversation lock. Durable event writes take the lock
  only to allocate ordered sequence numbers.
- Do not recreate parallel persona pipelines or hidden tool defaults. Extend the current
  candidate-profile, coordinator, and target-assessment seams.
- Remove tests with deleted behavior; retain evidence, safety, persistence, and visible
  contract coverage.
